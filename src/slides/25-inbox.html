What we changed

One inbox per worker

One dispatcher is the only reader of the shared queue. Each worker reads only its own inbox.

No shared lock

Only the dispatcher touches the shared queue, and it is a thread that does not get killed on its own.

A worker dies

It can only block its own inbox, which is thrown away. The dispatcher stops sending to it. The others keep working.

A replacement starts

The supervisor starts a new worker with a fresh inbox. Its unfinished requests are sent again.

No shared lock between processes that can be killed. Since this change, the pool has not hung.

The fix is not a safer lock. Holding a lock when you are killed is how the primitive works. The fix is to take the shared lock away from anything that can be killed. One dispatcher, a thread in the pool, is the only reader of the shared queue. It hands each request to a free worker by putting it in that worker's own inbox. Each worker reads only its own inbox.

Now kill a worker. The worst it can do is block its own inbox, and that inbox is thrown away with it. The dispatcher sees the worker is gone and stops sending to it. The other workers never shared anything with it, so they keep working.

The supervisor starts a new worker with a fresh, empty inbox, and the requests the dead worker owed come back as system errors and are sent again. The rule we took from this: never share a lock with a process that can die. Since the change, the same kill test has not hung once, and with one of four workers killed all 40 test images were committed. One limit we state honestly: results still travel back on shared queues, so the same kind of failure is possible there, in a much narrower window.
