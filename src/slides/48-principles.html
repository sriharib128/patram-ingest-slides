What we learned

Six lessons from running for weeks

Expect failure. It’s not an anomaly

Over weeks, every step crashes midway at some point. Design for it.

Single responsibility

Each component does one job. A stage only transforms a sample; retries, coordination and scaling live in the engine.

Follow every error through

Every error ends somewhere: retried, or set aside with a reason. Nothing stays stuck.

Nothing ever waits forever

A crashed process can’t release a lock. So workers share no locks: each gets its own inbox.

The right parallelism for each job

Processes compute, threads wait, event loops juggle calls.

Keep the database light

Only state in the database. Results go to files, written in groups.

If you take six things away from this talk, these are the lessons we learned the hard way.

One: expect failure; it is not an anomaly. Over weeks on a shared cluster, every step will at some point crash in the middle, so design every step for that, instead of treating it as a rare exception.

Two: single responsibility. Every component does exactly one job. A stage only transforms a sample: it does not know the graph, retry, coordinate or scale. Those live once in the engine, which is why a new pipeline is a few lines of code, and why a bug in one stage cannot break recovery.

Three: follow every error through to the end. Every error lands somewhere definite: a system problem is retried, a bad sample is set aside with its reason, and if you cannot tell which, you retry, because a retry costs seconds and a good sample thrown away is gone. Nothing is left stuck in between.

Four: nothing ever waits forever. A process that is killed while holding a shared lock never releases it, and every other worker blocks on it for good. So nothing that needs a lock is shared between workers that can die: each worker gets its own private inbox, and no process can end up stuck waiting on one that is gone.

Five: use the right parallelism for each job. Processes for computing, threads for waiting, event loops for many calls at once.

Six: keep the database light. It holds only state; the results go to files on each node, written in groups, off the GPU's path. That is why the system keeps scaling as nodes are added.
